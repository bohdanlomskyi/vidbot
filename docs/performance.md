# Melody — аудит производительности и надёжности (2026-11-06)

Замеры сделаны в контейнере Linux (Node.js 24.22.1, FFmpeg 6.1.1). Версии «до» и «после» прогонялись одними и теми же скриптами из `bench/`: «до» — в отдельном worktree коммита `cdaeec6`, «после» — на текущей ветке. Discord в замерах заменён подделкой. Сеть, голосовой шлюз и DAVE в них не участвуют.

Повторить замеры:

```bash

npx tsx bench/hotpaths.bench.ts
```

## Что изменено и почему

### Кодирование Opus вне основного потока

До: PCM из FFmpeg подавался в `createAudioResource(StreamType.Raw, inlineVolume)`, и громкость с кодированием Opus выполнялись в основном потоке. Тот же поток обслуживает команды, события Discord и таймер отправки голосовых пакетов (каждые 20 мс). Кодирование идёт пачками по ~17 кадров на блок из FFmpeg, так что при нескольких одновременных потоках оно задерживает и команды, и отправку пакетов.

После: один общий worker thread (`src/audio/opus/opusWorkerEncoder.ts`) держит по кодеру libopus на поток и применяет громкость. Плеер получает готовые пакеты (`StreamType.Opus`).

Рассмотренная альтернатива: кодирование Opus в самом FFmpeg (`-c:a libopus -f ogg`). Оно сокращает CPU основного потока сильнее (до 0,24 мс на секунду звука), но громкость тогда задаётся фильтром FFmpeg, и каждое её изменение требует перезапуска процесса. Для сетевых источников перезапуск невозможен без повторной загрузки. Вариант отклонён.

Цена: около 27 МБ памяти, пока играет музыка, и +5 % суммарного CPU на передачу данных между потоками. Для одного сервера выигрыш небольшой (~0,8 % ядра). Он растёт с числом одновременных потоков. Если worker не запускается, бот работает по-старому.

### Загрузка трека вне блокировки сервера

До: открытие источника (`getPlayableStream`, для YouTube — запуск yt-dlp и ожидание первых байтов) шло под блокировкой сервера. Все команды и голосовые события этого сервера ждали, на YouTube — секунды при каждой смене трека.

После: источник открывается вне блокировки, а результат применяется под ней, только если трек всё ещё текущий.

### Таймаут загрузки

До: движок переставал ждать через 20 секунд, но не отменял провайдер. У YouTube собственный таймаут — 30 секунд. Если первые байты приходили между 20-й и 30-й секундой, источник открывался, но его никто не закрывал. FFmpeg и yt-dlp блокировались на заполненных каналах и оставались навсегда вместе со слотом YouTube. Две такие утечки при `YOUTUBE_MAX_CONCURRENCY=2` полностью выключали YouTube.

После: по таймауту движок отменяет `AbortSignal`, а источник, открывшийся позже, закрывает. Ожидание слота YouTube тоже прерывается отменой.

### Discord API

- Обновления панели одного сервера идут по очереди. Раньше два перекрывающихся обновления могли оба создать сообщение панели.
- Правка пропускается, если на панели ничего не изменилось. Позиция воспроизведения сама по себе не повод: это лишь отметка на момент отрисовки, а не живой счётчик.
- Голосовые события участников передаются движку, только если затрагивают канал бота.

### Поиск по библиотеке

До: на каждый запрос все строки каталога приводились к нижнему регистру, а все совпадения сортировались через `localeCompare`. После: строки поиска приводятся к нижнему регистру один раз, а индекс хранится в порядке названий, так что один проход раскладывает результаты по рангам без сортировки. Ранжирование не изменилось, это закреплено тестами.

## Что измерено и оставлено как есть

- `settings.get` (INSERT OR IGNORE + SELECT в SQLite) занимает около 6 мкс. Вызовов — единицы на событие. Кэш добавил бы сложность инвалидации без заметного выигрыша.
- Сессии серверов, где бот когда-либо играл, хранятся в памяти до перезапуска (несколько килобайт на сервер, без таймеров и процессов). Удаление сессии сбрасывало бы громкость и режим повтора, которые пользователь ждёт сохранёнными. Поэтому поведение оставлено.

## Запуск трека YouTube (добавлено 2026-11-07)

Измерено на реальном YouTube из среды разработки (yt-dlp 2026.10.26, Node 24.22.1): один разбор страницы видео (метаданные) занимает около 3,5 секунды (два замера: 3,58 и 3,47 с, до ответа). Раньше `/play <ссылка>` запускал yt-dlp дважды подряд: сначала метаданные, затем поток, и каждый запуск заново разбирал страницу. Теперь, когда трек стартует сразу, обе задачи выполняет один процесс.

- Ожидаемый выигрыш: одна из двух задержек, то есть порядка 3,5 секунды из 7 на машине с такой же скоростью разбора. Это оценка по времени разбора, а не измерение полного запуска: из среды разработки YouTube не отдаёт звук (проверка «не бот»), поэтому сквозной замер невозможен. Проверьте на своём компьютере.
- Выбор из результатов поиска метаданных не запрашивает: они уже есть, остаётся один запуск потока.
- Поиск: 2,2 с на запрос (реальный YouTube), повтор того же запроса в течение 5 минут отдаётся из кэша.
- Доказано: в режиме `-o -` yt-dlp печатает `--print` в stderr, а звук в stdout, и `--no-simulate` не даёт `--print` отключить загрузку (проверено на локальном файле).

## Скорость ответов, панели и смены треков (1.2.0, 2026-11-07)

- **Ответ на команду — один запрос вместо трёх.** В 1.1.0 команда делала `deferReply` → `followUp` → `deleteReply`, и из-за поведения Discord публичный результат оставался приватным. Теперь быстрое действие (пауза, пропуск, громкость, кнопки панели) отвечает одним `reply`. Приватная заглушка появляется, только если работа длится дольше 1,5 с.
- **Панель.** Задержка объединения обновлений снижена с 1000 до 250 мс. Новая панель отправляется до удаления старой, так что пользователь видит её сразу. Пока панель — последнее сообщение, она правится одним запросом.
- **Смена трека YouTube.** Следующий трек открывается за 15 с до конца текущего (`preload`), поэтому переход не ждёт новый запуск yt-dlp (около 3,5 с на разбор страницы в замере). Проверено на поддельном yt-dlp: предзагруженный трек играет из уже запущенного процесса, без второго запуска. На настоящем YouTube выигрыш не измерен.
- **FFmpeg: измерено и оставлено как есть.** Время до первого байта PCM при подаче через канал (как у YouTube и потоков) для webm/opus, m4a и mp3, со скоростью подачи 200 КБ/с и 2 МБ/с: 45–130 мс со стандартными настройками и столько же с `-probesize 32k -analyzeduration 0 -fflags nobuffer`. Выигрыша нет, а риск неверного определения формата есть, поэтому флаги не добавлены.
- **Не делалось сознательно:** запуск первого результата поиска до выбора. Это лишний запрос к YouTube на каждый поиск и повышенный риск проверки «не бот», при выигрыше только если выбран именно первый вариант.

## Что не измерено

- Задержка и джиттер голосовых пакетов в настоящем голосовом канале Discord.
- Время старта трека YouTube на реальной сети: из этой среды YouTube недоступен. Первый трек по-прежнему ждёт запуск yt-dlp (несколько секунд); следующие открываются заранее. Насколько надёжно соединение с YouTube переживает 15 секунд простоя до начала воспроизведения, не проверено. Если заранее запущенный процесс завершился с ошибкой до начала трека, он отбрасывается, и трек открывается обычным путём; обрыв уже во время воспроизведения обрабатывается как любой оборванный поток.
- Работа под Windows и macOS.
