# Melody — архитектура и проектные решения

Документ фиксирует решения, которые влияют на дальнейшее развитие бота. Версии зависимостей проверены по npm registry и по установке в этом репозитории на дату 2026-11-05. Раздел 18 описывает, что проверено на живом Discord и что нет.

## 1. Цели и границы

- Музыкальный бот для нескольких Discord-серверов. Каждый сервер получает независимую сессию: очередь, плеер, голосовое соединение, таймеры и панель.
- Источники аудио: локальная библиотека (обязательна), каталог потоков оператора (выключен по умолчанию), экспериментальный YouTube через yt-dlp (выключен по умолчанию).
- Вне проекта: ИИ-чат, платные функции, аккаунты пользователей, Spotify, self-bot, Message Content Intent, запись или анализ микрофонов участников.

### Зависимости и безопасность

- `overrides` в `package.json`:
  - `tar: ^7.5.22`. Старый `tar` 6.x тянулся через `@discordjs/node-pre-gyp` с критическими и высокими уязвимостями распаковки.
  - `minimatch: ^11.0.4`. Уязвимость ReDoS в диапазоне `<11.0.1` затрагивала ESLint и typescript-eslint.
- `npm audit` после overrides: 0 уязвимостей.
- Install-скрипты трёх пакетов (`@discordjs/opus`, `better-sqlite3`, `esbuild`) подтверждены в `allowScripts`.
- Предупреждения `npm` о deprecated-пакетах из цепочки `@discordjs/node-pre-gyp` (`rimraf@3`, `glob@7`, `npmlog`, `inflight`) остаются. Эти пакеты используются только при установке нативного модуля.

### Почему не opusscript и не node:sqlite

- `opusscript` последний раз публиковался в октябре 2023 года. Для Opus используется `@discordjs/opus`.
- `node:sqlite` ещё экспериментальный. Для SQLite используется `better-sqlite3` с готовыми бинарниками и зрелыми типами.

### Шифрование голоса

`@discordjs/voice` 0.19 выбирает режим `aead_aes256_gcm_rtpsize`, если Node поддерживает `aes-256-gcm`. Отдельные libsodium-пакеты не нужны. Проверка есть в `npm run doctor`: шифр присутствует и выполняет круговой тест.

## 4. Поток команды `/play`

1. Маршрутизатор проверяет rate limit пользователя (ключ — сервер и пользователь). Команда отклоняется до выполнения обработчика.
2. Обработчик сначала подтверждает взаимодействие (`deferReply` с ephemeral-флагом), чтобы уложиться в 3 секунды.
3. Ввод нормализуется: обрезаются пробелы, отвергаются управляющие символы и строки длиннее 500 символов.
4. `SourceRouter` выбирает провайдер и проверяет, что источник разрешён на сервере:
   - ссылка YouTube: `YouTubeExperimentalProvider`;
   - идентификатор из каталога потоков: `AuthorizedStreamProvider`;
   - идентификатор `lib-…` или текст: `LocalAudioProvider`.
5. `provider.resolve()` выполняется вне блокировки сессии и с таймаутом 20 секунд. Медленная ссылка не блокирует `/pause` и `/skip`.
6. Внутри блокировки сессии (`KeyedMutex` по guildId) выполняются проверки:
   - `evaluateAccess` проверяет право пользователя;
   - при необходимости подключение к каналу. Бот не переносится, если он занят в другом канале;
   - `TrackQueue` проверяет лимит очереди, длительность трека проверяется до подключения;
   - если сессия свободна, начинается загрузка первого трека.
7. Источник открывается **вне блокировки** (`load` в движке): `/volume`, `/pause`, `/queue` и голосовые события не ждут, пока YouTube или поток отдадут первые байты. Результат применяется под блокировкой и только если трек всё ещё текущий. Если за это время трек пропустили или остановили, открывшийся источник закрывается.
8. Загрузке отводится 20 секунд. По истечении срока провайдер отменяется через `AbortSignal`, а источник, открывшийся позже, закрывается. Так медленный источник не оставляет процессы FFmpeg и yt-dlp.
9. `enqueue` ждёт исхода первого трека, не держа блокировку. Если трек не запустился, ответ называет причину («Не удалось воспроизвести «…»: …»), а не номер в очереди.
10. Ответ сначала приватный (ephemeral). При успехе он заменяется коротким публичным сообщением с упоминанием участника (`confirm` в `actionContext`), если режим `/settings announce` это разрешает; иначе остаётся приватным. Ошибки всегда приватные. Панель обновляется через `PanelManager` с задержкой 1 секунда.

Дополнения этого потока:

- **Поиск.** Если ввод не ссылка, не идентификатор и не точное название трека из библиотеки, а YouTube включён и разрешён на сервере (`SourceRouter.wantsSearch`), `/play` не открывает трек, а ищет `ytsearch8:` и показывает до 5 вариантов (`searchPicker`). Метаданные берутся из результатов поиска, поэтому выбор запускает ровно один процесс yt-dlp. Список привязан к участнику, живёт 2 минуты и расходуется при выборе. Результаты поиска кэшируются на 5 минут.
- **Быстрый старт по ссылке.** Если трек начнёт играть сразу (бот свободен), `resolve` получает признак `willPlayNow`. Провайдер запускает yt-dlp один раз: метаданные приходят JSON-строкой в stderr (`--print` вместе с `--no-simulate`), звук в stdout. Процесс ждёт плеера до 45 секунд и удерживает слот потока. Если свободного слота нет, используется прежний путь с отдельным запросом метаданных.
- **Файл.** Поле `file` команды `/play`: `UploadService` скачивает вложение только с `cdn.discordapp.com` и `media.discordapp.net`, считает размер при скачивании, проверяет содержимое ffprobe, сохраняет в `music/uploads` под очищенным именем (идентичный файл не дублируется), обновляет каталог и ставит трек в очередь как обычный трек библиотеки.
- **Панель и чат.** `PanelManager` ведёт панель в канале последней команды (`ChannelFollower`), а при новом треке пересоздаёт сообщение внизу чата. Закреплённый `/setup` канал имеет приоритет. События движка (`track_failed`, `left_channel`, `connection_lost`, `connection_restored`, `queue_finished`, `moved`) превращаются в сообщения через `describeEngineEvent`.

## 5. Состояния сессии

Состояния: `idle`, `connecting`, `buffering`, `playing`, `paused`, `error`, `disconnected`, `destroyed`. Допустимые переходы заданы таблицей `TRANSITIONS` в `src/music/session/playbackState.ts`:

| Из             | Допустимо в                                                          |
| -------------- | -------------------------------------------------------------------- |
| `idle`         | `connecting`, `buffering`, `disconnected`, `destroyed`               |
| `connecting`   | `idle`, `buffering`, `error`, `disconnected`, `destroyed`            |
| `buffering`    | `playing`, `idle`, `error`, `buffering`, `disconnected`, `destroyed` |
| `playing`      | `paused`, `buffering`, `idle`, `error`, `disconnected`, `destroyed`  |
| `paused`       | `playing`, `buffering`, `idle`, `error`, `disconnected`, `destroyed` |
| `error`        | `idle`, `buffering`, `disconnected`, `destroyed`                     |
| `disconnected` | `connecting`, `idle`, `playing`, `paused`, `buffering`, `destroyed`  |
| `destroyed`    | —                                                                    |

Недопустимый переход отвергается, а не применяется молча. Таблица покрыта тестами. Каждое воспроизведение получает `playbackToken`. События плеера и таймеров с устаревшим токеном игнорируются, поэтому один трек не может дважды запустить следующий.

События плеера, голосового соединения и таймеров обрабатываются через `background()`: задача выполняется под блокировкой сервера, а её ошибка пишется в журнал. Раньше такая ошибка становилась необработанным отказом, и обработчик процесса останавливал весь бот.

Трек, который закончился, ни разу не дойдя до `playing` (пустой или повреждённый файл), считается ошибкой, а не завершением. Иначе в режиме «повтор трека» он перезапускался бы без остановки.

## 6. Очередь и повтор

- В `TrackQueue` хранятся только ожидающие треки. Текущий трек хранится отдельно.
- Лимит `MAX_QUEUE_SIZE` по умолчанию 100, жёсткий максимум 500. Меняется командой `/settings queue-limit`.
- `/remove <номер>` нумерует ожидающие треки с 1.
- `/shuffle` перемешивает только ожидающие треки. Алгоритм Фишера–Йетса с инжектируемым генератором для тестов.
- Режим `track`: завершённый трек запускается снова. Пропуск выводит из режима повтора только этот проход.
- Режим `queue`: завершённый трек и пропущенный трек ставятся в конец очереди. Трек с ошибкой воспроизведения в конец не возвращается.
- `/stop` и `/leave` очищают очередь. Очередь не восстанавливается после перезапуска процесса.
- Конкурентные `/play` выполняются по очереди внутри блокировки сессии. Лимит проверяется внутри блокировки, поэтому лишние треки не проходят.

## 7. Аудиопровайдеры

### 7.1 Контракт

```ts
interface AudioProvider {
  readonly kind: 'local' | 'stream' | 'youtube';
  readonly enabled: boolean;
  canHandle(input: string): boolean; // синхронно, без сети
  resolve(input: string, ctx: ResolveContext): Promise<readonly TrackDraft[]>;
  validate(track: Track): Promise<void>; // перед запуском
  getPlayableStream(track: Track, signal: AbortSignal, startSec?: number): Promise<PlayableSource>;
  dispose(): Promise<void>;
}

interface PlayableSource {
  readonly stream: Readable; // PCM s16le, 48 кГц, стерео
  readonly ended: Promise<PlaybackEnd>; // completed | stopped | failed
  close(): Promise<void>; // останавливает дочерние процессы
}
```

`TrackDraft` содержит `source`, `sourceRef` (стабильная ссылка провайдера), `title`, `artist`, `durationSec` (`null` для эфира), `thumbnailUrl`, `originalUrl` (только для отображения и только там, где это безопасно), `metadata` (без URL потоков и секретов). Очередь добавляет `id`, `requesterId` и `createdAt`.

FFmpeg всегда запускается через `spawn` с массивом аргументов, shell не используется. Вход либо файл из библиотеки, либо stdin, куда провайдер передаёт данные. Для файлов включён только протокол `file`, для stdin только `pipe`.

### 7.2 LocalAudioProvider

- Каталог `MUSIC_DIR` (по умолчанию `music/`). Сканирование рекурсивное, глубина до 5, до 5000 файлов. Расширения: mp3, flac, wav, ogg, oga, opus, m4a, aac.
- Симлинки пропускаются. Путь проверяется через `realpath`: файл должен оставаться внутри `MUSIC_DIR`.
- Идентификатор: `lib-` и первые 12 шестнадцатеричных символов SHA-256 относительного пути. Пути пользователям не показываются и от них не принимаются.
- Метаданные через `ffprobe`: длительность, теги `title` и `artist`. Каталог хранится в SQLite. Файл анализируется повторно только при изменении размера или времени изменения.
- Поиск по тексту сопоставляет название, исполнителя и имя файла, с ранжированием «точное совпадение, затем префикс, затем содержание». Неоднозначный ввод отклоняется с просьбой выбрать вариант из подсказок.
- `validate()` проверяет, что файл существует и находится внутри каталога библиотеки.
- Пересканирование: при запуске и каждые `MUSIC_RESCAN_MINUTES` минут (0 отключает). Параллельные сканирования объединяются в одно.

### 7.3 AuthorizedStreamProvider

- Выключен по умолчанию (`STREAM_PROVIDER_ENABLED=false`). Каталог оператора `config/streams.json` валидируется zod. Пример: `config/streams.example.json`.
- Запись каталога: `id` (строчные латинские буквы, цифры и дефис, 3–40 символов, без префикса `lib-`), `title` (до 100 символов), `artist` (до 100 символов, необязательно), `url`, `allowHttp` (по умолчанию `false`), `allowedHosts` (по умолчанию хост из `url`), `allowedPorts` (необязательно), `live`, `durationSec`, `thumbnailUrl`.
- Каждая запись проверяется отдельно: одна ошибка не отключает остальные. Повторный идентификатор пропускается. Сообщения оператору называют запись, но не показывают адрес.
- Поток получает Node по HTTP(S), а не FFmpeg. Байты передаются в stdin FFmpeg.
- SSRF-защита:
  - схема `https`, `http` только при `allowHttp: true`;
  - в URL нет учётных данных, порт 80 или 443, либо порт из `allowedPorts`;
  - адреса проверяются в DNS-коллбэке при установлении соединения. Допустим только публичный одноадресный адрес; loopback, private, link-local (включая 169.254.169.254), CGNAT, multicast, reserved, IPv6 ULA и mapped-адреса отклоняются;
  - перенаправления выполняются вручную, не более трёх, и каждое проверяется заново;
  - тайм-ауты: ответ (заголовки) 15 секунд, простой данных 15 секунд;
  - тип содержимого должен быть аудио; HTML и JSON отклоняются;
  - конечные потоки ограничены `STREAM_MAX_BYTES` (по умолчанию 512 MiB). Прямые эфиры (`live: true`) лимита байт не имеют, но простой ограничен таймаутом.
- URL потоков не попадают в журнал, ответы пользователям и `/status`.

### 7.4 YouTubeExperimentalProvider

Статус: экспериментальный, выключен по умолчанию, на реальных видео не проверен. Правила: [docs/youtube.md](youtube.md).

- Принимаются ссылки `youtube.com`, `m.youtube.com`, `music.youtube.com`, `youtu.be`, Shorts и плейлисты. Из ссылки извлекается идентификатор видео или плейлиста, он проверяется регулярным выражением, затем строится канонический URL. Произвольный пользовательский URL в yt-dlp не передаётся.
- Базовые флаги yt-dlp: `--ignore-config --no-update --no-warnings --no-progress --js-runtimes <node|deno> --cache-dir <data> --socket-timeout 20`, затем `--` и канонический URL. Флаги `--cookies`, `--proxy`, `--downloader` и пользовательские аргументы не используются.
- Метаданные: `--no-playlist --skip-download --dump-single-json`. Звук: `--no-playlist -f bestaudio/best -o -`, вывод в stdout, далее FFmpeg из stdin. Когда трек начнёт играть сразу, обе задачи выполняет один запуск: `... --print '%(.{id,title,duration,...})j' --no-simulate -o -` (метаданные приходят строкой в stderr).
- Поиск: `--flat-playlist --dump-single-json -- ytsearchN:<запрос>`. Запрос идёт после `--` и префикса `ytsearchN:`, поэтому он никогда не читается как флаг; управляющие символы и длина свыше 200 символов отклоняются. Проверено на реальном YouTube из среды разработки (2,2 с на запрос).
- Плейлист: `--flat-playlist --yes-playlist --playlist-end <N> --dump-single-json`, не более `YOUTUBE_PLAYLIST_MAX_ITEMS` элементов.
- Прямые эфиры и предстоящие трансляции (`is_live`, `is_upcoming`, `post_live`) отклоняются.
- Ограничения: `YOUTUBE_MAX_DURATION_SEC` (по умолчанию 900), `YOUTUBE_MAX_CONCURRENCY` (по умолчанию 2), `YOUTUBE_TIMEOUT_SEC` (по умолчанию 30). Лимит действует отдельно для потоков (слот удерживается всё время воспроизведения) и для запросов метаданных, поэтому ссылки разрешаются, даже когда все потоковые слоты заняты. Одновременно работает не больше `2 × YOUTUBE_MAX_CONCURRENCY` процессов yt-dlp. Ожидание слота прерывается отменой трека.
- Circuit breaker: после пяти подряд системных ошибок провайдер приостанавливается на 10 минут. Успешный запрос сбрасывает счётчик. Ошибки уровня видео (приватное, удалённое, возрастное) в счётчик не входят.
- Текст stderr переводится в короткие русские сообщения. Сырой stderr пользователю не показывается.
- Не обходятся ограничения: PO-токены, cookies, прокси, DRM, возрастные и региональные ограничения, платный контент. При таких ограничениях бот сообщает об ошибке и продолжает работать.

## 8. Голос и DAVE

- `DiscordVoicePort.connect` вызывает `joinVoiceChannel` с `selfDeaf: true` и ждёт состояния `Ready` не дольше 15 секунд. При неудаче соединение уничтожается.
- У сервера Discord одно голосовое соединение, и `joinVoiceChannel` возвращает уже существующее. Поэтому перенос (`/move`, перенос ботом-администратором) выполняется через `rejoin()` того же соединения, и движок получает тот же объект. Движок уничтожает «предыдущее» соединение, только если это действительно другой объект. До исправления перенос уничтожал живое соединение: бот выходил из канала, а движок считал его подключённым.
- Канал соединения читается из `joinConfig` библиотеки, которая сама следит за голосовым состоянием бота. Если администратор перетащил бота, движок обновляет канал сессии и считает слушателей уже в новом канале.
- Если соединение разорвано, библиотека сначала пытается восстановить его: до 5 секунд ждёт `Signalling` или `Connecting`. Если не вышло, соединение считается потерянным. Причина `kicked` выставляется при коде закрытия 4014 (бота отключили или переместили), иначе `disconnected`.
- Движок после потери соединения пробует переподключиться не более трёх раз, с паузами 1, 3 и 8 секунд. При неудаче сессия покидает канал и сообщает об этом в панели и журнале.
- Событие смены голосового состояния самого бота передаётся движку. Если бота отключили, сессия очищается с причиной `kicked`. Если бота перенесли, движок переподключается к новому каналу. Если переподключиться не удалось, сессия завершается с причиной `lost`.
- Право `Connect` и `Speak` проверяется перед подключением и перед запуском трека. Без них пользователь получает понятное сообщение.
- Звук: PCM из FFmpeg кодируется в Opus в отдельном потоке (`OpusWorkerEncoder`, один worker thread на весь процесс), там же применяется громкость. Плеер получает готовые пакеты (`StreamType.Opus`). Изменение громкости действует сразу, без перезапуска FFmpeg и без лишних процессов. У каждого потока не больше одного блока в работе, поэтому обратное давление доходит до FFmpeg. Worker останавливается после минуты без потоков (возвращая около 27 МБ памяти) и запускается со следующим треком. Если worker не стартует, используется прежний путь: `StreamType.Raw` с встроенной громкостью @discordjs/voice. Громкость от 0 до 100 процентов переводится в усиление от 0 до 1, усиления сверх 100 процентов нет. Замеры — в `docs/performance.md`.
- DAVE: шифрование выполняет `@discordjs/voice` вместе с `@snazzah/davey`. Криптография в приложении не реализуется. В этой среде проверены загрузка библиотеки и создание сеанса с ключевым пакетом. Рукопожатие с сервером Discord не выполнялось.

## 9. Права доступа

Термины:

- **слушатель** — человек (не бот) в голосовом канале бота;
- **DJ** — участник с ролью, заданной в `/settings dj-role`;
- **администратор** — участник с правом Manage Server или Administrator;
- **единственный слушатель** — пользователь, который один в канале бота.

Политика вычисляется чистой функцией `evaluateAccess(action, actor, context, target?)` в `src/security/accessPolicy.ts`.

| Действие                                                                       | Режим `everyone` (по умолчанию)                                 | Режим `dj`           |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------- | -------------------- |
| `/queue`, `/nowplaying`, `/history`, `/help`, `/status`                        | все                                                             | все                  |
| `/play`, `/playlist`, `/replay`, `/join`                                       | любой в голосовом канале. Если бот занят в другом канале, отказ | то же                |
| `/pause`, `/resume`, `/skip`, `/shuffle`, `/loop`, `/volume`, перезапуск трека | слушатель                                                       | DJ или администратор |
| `/skip` при включённом голосовании                                             | слушатель, голос учитывается, если слушателей больше одного     | DJ или администратор |
| `/remove` своего трека                                                         | добавивший трек                                                 | добавивший трек      |
| `/remove` чужого трека, `/clear`, `/stop`, `/leave`                            | DJ, администратор или единственный слушатель                    | DJ или администратор |
| `/move`                                                                        | DJ или администратор                                            | DJ или администратор |
| `/setup`, `/settings`                                                          | администратор                                                   | администратор        |

Бот занят, если в его канале играет музыка, есть очередь или слушатели. В этом случае `/play` и `/join` из другого канала отклоняются. Бот не переносится по инициативе обычного пользователя.

Команды работают только на сервере. Права проверяются перед каждым действием, а не один раз при подключении.

## 10. Автоотключение

- `empty`: таймер по умолчанию 60 секунд. Запускается, когда в канале бота нет слушателей, и отменяется при появлении слушателя.
- `idle`: таймер по умолчанию 300 секунд. Запускается, когда ничего не играет и очередь пуста, и отменяется при добавлении трека.
- Оба значения настраиваются через `/settings empty-timeout` и `/settings idle-timeout`.
- Для каждого вида таймера в сессии есть не более одного экземпляра. Повторный запуск того же вида ничего не делает, поэтому обратный отсчёт не удваивается.
- При уничтожении сессии все таймеры отменяются.
- Боты не учитываются как слушатели.

## 13. Ошибки и устойчивость

- Пользовательские ошибки (нет прав, неверный ввод, приватное видео) возвращаются коротко, без стеков.
- Системные ошибки записываются в журнал с контекстом. Пользователю показывается общий текст.
- Повторов немного. Единственный автоматический повтор — восстановление голоса: до трёх переподключений. Для потоков и подключения к каналу повторов нет. Ошибка возвращается сразу.
- Если трек не удалось открыть или он оборвался с ошибкой, в панели выводится короткое сообщение, а сессия переходит к следующему треку из очереди.
- Сбой YouTube не останавливает бота: провайдер изолирован и защищён circuit breaker.
- Ошибки обработчиков взаимодействий перехватываются маршрутизатором. Если ответ не доставлен, это записывается в журнал.
- Панель обновляется не чаще одного запроса на сервер за раз: обновления одного сервера выполняются по очереди, поэтому два обновления не создают два сообщения панели. Правка пропускается, если на панели ничего не изменилось (позиция воспроизведения сама по себе не повод). Голосовые события участников передаются движку, только если они касаются канала бота.

## 14. Наблюдаемость

- Логи pino в формате JSON на стандартный вывод. Уровень задаётся `LOG_LEVEL`. Секреты маскируются по точному значению токена и по именам полей.
- Записываются запуск и остановка, вход в Discord, регистрация команд, подключение к голосу, переходы состояний, переход к следующему треку, ошибки источников, восстановление, сканирование библиотеки.
- Heartbeat: файл `HEALTH_FILE` обновляется каждые 30 секунд. Статусы: `starting` до входа, `ready` после готовности клиента, `stopping` при остановке. Запись атомарная: через временный файл и переименование.
- Docker healthcheck и `scripts/healthcheck.js` проверяют, что статус `ready` и файл обновлялся не более 90 секунд назад.
- `npm run doctor` проверяет: версию Node.js (не ниже 24.17.0), конфигурацию (только факт наличия токена), FFmpeg и ffprobe, каталог библиотеки, каталог данных, базу (миграции и `quick_check`), Opus, DAVE, шифрование AES-256-GCM, при включённом YouTube — yt-dlp, при включённых потоках — каталог потоков. Код возврата ненулевой при ошибке.

## 15. Развёртывание

- Локально: Node.js 24, FFmpeg, `npm ci`, `npm run commands:register`, затем `npm run dev` или `npm run build && npm start`.
- Docker, основной способ на сервере: многоэтапная сборка на `node:24.22.2-trixie-slim`. FFmpeg из Debian. Запуск от пользователя `node`. Опционально yt-dlp с проверкой контрольной суммы (`YTDLP_SHA256` обязателен, если указан `YTDLP_VERSION`).
- `compose.yaml`: `init: true`, `restart: unless-stopped`, `read_only: true`, `cap_drop: ALL`, `no-new-privileges`, `tmpfs` для `/tmp`, `music` и `config` только для чтения, данные в именованном томе `melody-data`, входящие порты не публикуются, журнал ограничен 10 МБ по три файла.
- Секреты передаются через `env_file` из `.env`. В образ и в `compose.yaml` они не попадают.
- Для работы 24/7 нужен постоянно работающий хост. Платформы, которые усыпляют контейнеры, для голосового бота не подходят.

## 17. Отклонения от исходного ТЗ

1. Node.js 24.22.2, а не минимальные 24.17.0. Так проще воспроизводить сборку. `engines` по-прежнему `>=24.17.0`.
2. TypeScript 6.0.3 вместо 7.x из-за peer-ограничения typescript-eslint.
3. `@discordjs/opus` вместо `opusscript`: `opusscript` не обновлялся с 2023 года.
4. `better-sqlite3` вместо `node:sqlite`: зрелые типы и предсобранные бинарники.
5. Overrides для `tar` и `minimatch`.
6. JSON-логи без `pino-pretty`. Зависимость не добавлена, чтобы не тянуть лишнее в production.
7. `.env` читается встроенным `process.loadEnvFile`, без пакета dotenv. Переменные из окружения имеют приоритет над файлом.
8. `/leave` очищает очередь, так же как `/stop`. Это проще и предсказуемее, чем сохранять очередь без слушателей.
9. `/volume` меняет громкость текущей сессии. Постоянная громкость задаётся через `/settings default-volume`.
10. `/playlist` поддерживает только плейлисты YouTube. Папки библиотеки в ТЗ не входили, и их поддержка не добавлялась.
11. Очередь не восстанавливается после перезапуска. Это следствие решения хранить очередь только в памяти.
12. Команда `/replay` использует тот же путь, что `/play`, и поэтому проверяет право «добавление».

- поиск YouTube с выбором из 5, запуск трека одним процессом yt-dlp, панель-плеер в чате с кнопками, сообщения о действиях и событиях, загрузка своих файлов, избранное, `/previous`, `/skipto`, `/play next`, режим 24/7;
- тесты: 58 файлов, 530 тестов, все проходят (`npm run check`);
- не реализовано сознательно: автоплей «похожих» (список связанных видео YouTube недоступен для проверки), аудиофильтры, тексты песен, Spotify и другие сервисы. Причины — в [competitors-and-plan.md](competitors-and-plan.md).

Найдено и исправлено при втором проходе:

- Остановка: интерфейс Discord больше не передаёт новые взаимодействия и голосовые события после начала остановки. Раньше они могли запустить работу, пока сессии уже сворачивались.
- Порядок остановки: панель отключается после движка. Раньше переходы сессии при остановке могли запланировать обновление панели уже после её отключения.
- Сбой обновления панели записывается в журнал. Раньше он становился необработанным отклонением, а обработчик процесса завершал бота.
- Описание `/playlist` приведено в соответствие с реализацией: поддерживаются только плейлисты YouTube.
- Описание архитектуры исправлено по коду: таймеры сессии не используют `unref`, повторы есть только у восстановления голоса, история хранит 200 записей.

- P1: загрузка трека шла под блокировкой сервера. Любая команда ждала до 20 секунд.
- P1: ошибка в обработчике события плеера или соединения останавливала весь процесс.
- P1: запросы метаданных YouTube ждали слотов, занятых играющими потоками, а отменённое ожидание позже всё равно запускало yt-dlp.
- P2: пустой трек в режиме «повтор трека» перезапускался без остановки.
- P2: два одновременных обновления панели могли создать два сообщения; правки без изменений и голосовые события из чужих каналов тратили запросы к API.
